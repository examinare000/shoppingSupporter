# ADR-004: エディトリアルデザインの採用とモック先行のフロントエンド開発

## ステータス
承認済み

## 背景
横断価格比較サービスは典型的に「フィルタ・チップ・グラデーション・絵文字」が並ぶ SaaS 然とした見た目になりがちで、視覚的な独自性とブランドの強さを得にくい。一方でバックエンド（FastAPI / 公式 API 連携 / Cron / DB）の整備にはリードタイムがかかり、UI の意思決定をバックエンドに引きずられると、初期にプロダクトの体験を確かめづらい。

## 決定

1. **紙面メタファのエディトリアルデザインを採用する。**
   - ブランドは `pricehack`（ドメインは `pricehack.net`）。ヒーロー見出しは `Where To Buy That?` の単一 h1。
   - フォントは Fraunces（ディスプレイセリフ）+ Newsreader（本文セリフ）+ JetBrains Mono（数字・キャプション）の三本立て。
   - カラーは紙色 + 濃インク + 朱赤 / 芥子色のアクセント（`globals.css` の CSS 変数）。紫グラデや絵文字でブランドを記号化することは避ける。
   - 紙の質感は SVG `fractalNoise` を全画面オーバーレイで再現し、追加のラスタ画像アセットを使わない。

2. **フロントエンドはバックエンド未接続のままモックデータで先行構築する。**
   - 商品・出品データは `frontend/lib/mock/products.ts` に置き、`searchClient.ts` がクライアントサイドで検索する。
   - 実質価格・出品ソート・画像優先度解決などのロジックは TDD（Vitest）で先に固める。
   - 環境変数（DB / 公式 API キー）が無くても `npm run dev` だけで UI が完全に動く状態を保つ。

3. **検索前は結果セクションを描画しない（表紙ティザー構成）。**
   - クエリが空のときはトップ画面に Masthead + HeroSearch + Footer のみが並ぶ。
   - 検索が走って初めて `SearchResultsSection` が出現する。

## 理由

- **デザイン**: 競合と差別化できる視覚的アイデンティティを得られる。読み物的な質感は「実質価格を読み解く編集記事」というプロダクトの性格にも合う。装飾は CSS 変数とフォント変数に集約し、後からトークンを差し替えやすい。
- **モック先行**: フロントの体験品質をバックエンドの完成を待たずに検証できる。型 (`types/product.ts`) と純粋関数 (`lib/pricing/`, `lib/format/`, `lib/image/`) を先に確定しておけば、後からバックエンドを差し込む際のインターフェース合意が速い。
- **表紙ティザー**: 旧版は検索前から全件結果を並べていたため、Masthead / HeroSearch / 結果リストが画面上で衝突していた。検索行為のあとに結果が立ち上がる方が情報設計として整理される。

## 影響

- **負債の所在を明示する**: 公式 API 連携が完成するタイミングで `lib/mock/` をどう削るか・スワップするかを別途決める必要がある。`searchClient` のシグネチャはバックエンド呼び出し版に置き換えやすい純粋関数の体裁を保つこと。
- **ロジックの責務分離**: フロントのプライシング計算はあくまで「素の式 (`price + shippingFee − points`) + 0 下限」に留める。ユーザー文脈（楽天ランク・Prime 加入・所有カード等）を加味した計算はバックエンド側で行い、フロントには算出済みの値を渡す方針とする。
- **モーション**: `prefers-reduced-motion: reduce` でアニメーションを無効化する設計を `globals.css` に集約。コンポーネント側ではキーフレームを定義してもメディアクエリ判定を都度書かなくてよい。
- **テスト**: Vitest + Testing Library + jsdom 構成。価格・整形・画像優先度の各ロジックは単体テストで先に書く（`agent-rules/11-testing-strategy.md` に整合）。
