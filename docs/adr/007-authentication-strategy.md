# ADR-007: ユーザー認証戦略の決定

## ステータス
採用済み

## 背景
`UserProfile` による実質価格のパーソナライズ機能を実装するためには、リクエスト主体の特定（認証）が必要である。Vercel Functions（サーバーレス）環境において、セッション管理のオーバーヘッドが少なく、セキュアかつ実装が容易な認証方式を選定する必要がある。

## 検討した選択肢

### 1. NextAuth.js (Auth.js)
- **メリット**: Next.js との親和性が極めて高く、多くのプロバイダーに対応。
- **デメリット**: バックエンド (FastAPI) とセッションを共有するために、Next.js 側でプロキシするか、共通の DB/Redis を参照して検証する手間が発生する。

### 2. FastAPI + JWT (ステートレス認証)
- **メリット**: バックエンドで完結。JWT 自体にユーザー情報を含められるため DB 問い合わせを減らせる。サーバーレス環境でステートレスに検証可能。
- **デメリット**: トークン失効（ログアウト/無効化）の管理がやや複雑。

### 3. Cookie ベースのセッション管理
- **メリット**: ブラウザ側のセキュリティ（HttpOnly/Secure）を最大限活用できる。
- **デメリット**: Redis 等の外部セッションストアが必要になり、サーバーレス環境では接続コストや管理の手間が増える。

## 決定
**選択肢 2（FastAPI + JWT）を採用する。**

- フロントエンド（Next.js）はログイン時に API から発行された JWT を受け取り、`localStorage` または `Cookie` に保存する。
- 以降のリクエストでは `Authorization: Bearer <token>` ヘッダーに載せて送信する。
- FastAPI 側は `PyJWT` を用いて、秘密鍵 (`JWT_SECRET`) で署名を検証し、ユーザー ID を抽出する。

## 理由
- **サーバーレス適正**: ステートレスな JWT 検証は、実行ごとに DB やセッションストアを叩く必要がないため、Vercel Functions のコールドスタートや実行時間の制約に対して有利である。
- **実装の簡潔さ**: Phase 1 の目的は「パーソナライズ計算」であり、認証自体に過度な工数をかけず、実績のある FastAPI の標準的な JWT パターンを採用するのが合理的と判断。

## 結果
- `JWT_SECRET` の管理が必須（`agent-rules/12-security-guidelines.md` 参照）。
- 認証が必要なエンドポイントでは `Depends(get_current_user)` を使用してクリーンに依存注入できる。
- 将来的に外部 IDP (Google 等) を追加する場合も、バックエンドで JWT を発行する構造を維持できる。
