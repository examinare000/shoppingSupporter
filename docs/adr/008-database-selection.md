# ADR-008: データベースサービスの選定

## ステータス
採用済み

## 背景
本プロジェクトは Vercel Functions (FastAPI) をバックエンドとして利用しており、これと相性が良く、かつ開発効率の高いマネージド PostgreSQL サービスを選定する必要がある。

## 検討した選択肢

### 1. Vercel Postgres
- **メリット**: Vercel との統合が完璧。プロビジョニングが不要。
- **デメリット**: 内部的には Neon を利用しており、独自機能や高度な設定へのアクセスが制限される場合がある。

### 2. Supabase
- **メリット**: Auth, Storage, Realtime など機能が豊富。無料枠が寛大。
- **デメリット**: 既に FastAPI でバックエンドを組んでいるため、Supabase 特有の機能（PostgREST 等）と役割が重複する。純粋な DB として使うにはやや冗長。

### 3. Neon (Serverless Postgres)
- **メリット**: Vercel Postgres のバックエンド。ブランチ機能が強力で、プルリクごとに隔離された DB 環境を作れる。PgBouncer が標準搭載されており、サーバーレスからの接続数問題に強い。
- **デメリット**: Vercel ダッシュボード外での管理が必要。

## 決定
**選択肢 3（Neon）を採用する。**

- インフラとして Neon を直接契約・利用する。
- ただし、本番環境の Vercel プロジェクトからは環境変数経由で接続し、Vercel のエコシステム（デプロイメント等）と連携させる。

## 理由
- **開発効率（ブランチ機能）**: GitHub のブランチに同期して DB をクローンできる Neon の機能は、スキーマ変更を伴う開発において極めて強力である。
- **コネクションプーリング**: サーバーレス環境特有の「多数の短寿命接続」を PgBouncer 経由で効率的に捌ける点が、信頼性につながる。
- **将来性**: プロジェクトが成長した際、Vercel Postgres の制約に縛られず、Neon 本体のフル機能を利用できる余地を残す。

## 結果
- `DATABASE_URL` は Neon から発行された、接続プール用エンドポイント (`-pooler`) を使用する。
- `.env` への反映と Alembic によるマイグレーション管理（T-01）が次のステップとなる。
