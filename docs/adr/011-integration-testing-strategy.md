# ADR-011: testcontainers と Alembic を活用したインテグレーションテスト戦略

## ステータス
採用済み

## 背景
バックエンド（FastAPI）の実装において、PostgreSQL 特有の機能（FTS, `pg_trgm`, `ARRAY` 型）を多用しており、標準的な SQLite in-memory テストでは機能の正しさを検証できない。また、マイグレーション（Alembic）が正しく適用されることや、実際の DB スキーマとの整合性を担保する必要がある。

## 決定
**`testcontainers-python` を導入し、本番環境と同等の Docker コンテナ（Postgres）を利用したインテグレーションテストを実施する。**

### 具体的なテスト方針
1.  **コンテナ管理**:
    *   `PostgresContainer` を使用し、テスト実行時に一時的な Postgres インスタンスを起動する。
    *   テスト実行速度を優先するため、コンテナはセッション単位（`scope="session"`）で使い回す。
2.  **スキーマ適用**:
    *   `Base.metadata.create_all` ではなく、実際のマイグレーションファイルを使用して `alembic upgrade head` を実行する。これにより、マイグレーションスクリプト自体の不備も検出する。
3.  **データ隔離**:
    *   各テストケースの実行前後でテーブルを `DELETE` (または `TRUNCATE`) し、テスト間の副作用を排除する。
4.  **依存注入**:
    *   FastAPI の `app.dependency_overrides` を活用し、プロダクション用の DB 接続をテスト用コンテナへの接続に差し替える。

## 理由
- **再現性**: 本番環境 (Neon) と同じ Postgres エンジンでテストを行うことで、SQL の互換性問題を早期に発見できる。
- **マイグレーションの信頼性**: 手書きのマイグレーションコードが失敗しないことを、コード変更のたびに自動検証できる。
- **メンテナンス性**: インフラ設定をコード（Docker イメージ）で管理できるため、CI 環境（GitHub Actions 等）でも容易に同一のテストを実行できる。

## 影響
- **実行環境**: テスト実行には Docker 実行環境が必要となる。
- **テスト速度**: コンテナの起動とマイグレーションの実行に伴い、SQLite に比べてテスト開始時のオーバーヘッド（数秒〜十数秒）が発生する。
- **リソース消費**: テスト実行中に Docker コンテナのリソース（CPU/メモリ）を消費する。
