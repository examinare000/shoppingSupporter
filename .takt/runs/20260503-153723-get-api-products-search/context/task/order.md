# タスク指示書: 商品検索エンドポイントの実装

## ゴール
`GET /api/products/search` を実装し、商品名・説明文・タグを対象にした Postgres 全文検索 + Trigram 併用の検索 API を提供する。

## スコープ

### 対象エンドポイント
- `GET /api/products/search`

### クエリパラメータ
| 名前 | 必須 | 内容 |
|------|------|------|
| `q` | 必須 | 検索キーワード |
| `inStock` | 任意 | 在庫ありフィルタ |
| `priceMin` | 任意 | 価格下限 |
| `priceMax` | 任意 | 価格上限 |
| `sort` | 任意 | ソート指定（選択肢は Planner が既存設計書から決定） |
| `page` | 任意 | ページ番号（1始まり） |

### ページネーション
- 1ページ 10件固定
- レスポンスに総件数・現在ページ・総ページ数を含める（具体的な envelope 形式は既存 API に合わせて Planner 判断）

### 検索ロジック（高）
- Postgres 全文検索（tsvector / tsquery）と Trigram（pg_trgm）の併用
- 検索対象カラム: 商品名・説明文・タグ
- 併用の組み立て方（UNION か OR 結合か、スコア合成か）は Planner 判断
- インデックス（GIN 等）が必要であればマイグレーションも本タスクのスコープに含める

### 返却フィールド
- 商品サマリのみ（具体項目は Planner が既存設計書から決定）

## 対象ファイル/モジュールごとの作業

### 高優先度
- **検索ルートハンドラ**: `GET /api/products/search` のハンドラを既存ルーティング規約に従って追加
- **検索クエリビルダ／リポジトリ**: 全文検索 + Trigram の SQL を組み立てるレイヤーを既存のデータアクセス層パターンに沿って追加
- **入力バリデーション**: `q` の必須チェック、`priceMin/Max` の数値・大小関係、`sort` の値域、`page` の正整数チェック
- **マイグレーション**: 必要なインデックス（tsvector カラム or 式インデックス、pg_trgm 用 GIN）を追加

### 中優先度
- **ソート実装**: Planner が決めた選択肢に対応する ORDER BY 分岐
- **フィルタ実装**: `inStock` / `priceMin` / `priceMax` の WHERE 条件
- **認証**: 認証要否は Planner が既存設計書から判断し、必要であれば既存ミドルウェアを適用
- **エラーハンドリング**: バリデーションエラー時のレスポンスを既存 API の規約に揃える

### 低優先度
- **ロギング**: 既存ロガーの慣習に合わせて検索クエリの発行を記録（ただし `q` 等のユーザ入力をそのままログに残す場合の扱いは既存ポリシーに従う）

## 確認方法 / 再現手順
1. ローカル DB にマイグレーションを適用
2. 商品データをシードに含めて起動
3. 以下の代表ケースを手動 or 統合テストで確認:
   - `?q=単語` で全文一致がヒット
   - `?q=部分文字` で Trigram によるあいまい一致がヒット
   - タイポを含むクエリでも近い商品がヒットする
   - `?q=...&priceMin=1000&priceMax=5000` で価格レンジが効く
   - `?inStock=true` で在庫ありのみ返る
   - `?sort=...` で並び順が切り替わる
   - `?page=2` で次の10件が返る
   - `q` 未指定 / 不正な数値 / 不正な `sort` 値 → バリデーションエラー

## Planner に委ねる判断事項
- 既存プロジェクト構成（ディレクトリ、フレームワーク、ORM、ルーティング規約）への組み込み方
- ソート選択肢の具体的な候補
- 返却サマリの具体的なフィールド定義
- 認証要否（既存設計書から判断）
- 全文検索と Trigram の併用方式（UNION / OR / スコア合成）の選択
- レスポンス envelope 形式（既存 API との整合）
- インデックス設計（tsvector カラム vs 式インデックス、generated column の採否 等）
